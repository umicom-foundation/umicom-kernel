Umicom Kernel guide

Allocate physical memory inside an address window

This Kernel course extends the existing physical-frame allocator. You will learn why enough free RAM does not always mean a particular request can succeed, how absolute alignment works, and how to test allocation without dereferencing a physical address. The implementation uses C and the Kernel's existing bitmap ownership authority.

Lesson 1: understand a physical frame

The allocator represents one contiguous RAM range as 4 KiB frames. Separate bitmaps record reserved frames and allocated frames. A reserved frame can hold the Kernel image or firmware data; an allocated frame belongs to an ordinary caller. The free count is an accounting result, not a guarantee of adjacency.

A request for four contiguous frames can fail even when twenty individual frames are free. Reservations, allocations and alignment may split the available space. Repeated single-frame allocation cannot promise a contiguous run and would need rollback after partial success. The native run allocator proves the whole run before changing ownership.

Lesson 2: state the address window explicitly

UmicomKernelPhysicalMemoryAllocateFramesInWindow adds an inclusive minimum address and an exclusive end. Both must be page aligned, the minimum must be below the end, and the entire window must be inside managed RAM. The service refuses an invalid window rather than silently clipping it.

UmicomAddress frame = 0;
UmicomKernelMemoryStatus status =
    UmicomKernelPhysicalMemoryAllocateFramesInWindow(
        2, 4, minimum_address, exclusive_end, &frame);
if (status == UMICOM_KERNEL_MEMORY_OK) {
    /* Own exactly two frames. Establish accessibility before using their bytes. */
    status = UmicomKernelPhysicalMemoryFreeFrames(frame, 2);
}

This fragment assumes the allocator is initialized, mandatory boot reservations are installed and the caller supplies admitted window bounds. The complete host tests show initialization and concrete bounds. A production caller must serialize all allocator access and check release errors.

Alignment is measured using the absolute physical frame number. With a 4 KiB page size and alignment of four frames, eligible addresses are multiples of 16 KiB. Starting the window at another page does not change that rule. The implementation divides by page size and tests the frame-number bits; it does not multiply an untrusted alignment into a potentially overflowing byte count.

Lesson 3: preserve one ownership authority

The unrestricted and windowed APIs share one bounded scan and one commit path. The original unrestricted implementation is retained in a disabled block for engineering review. Its current wrapper searches the entire managed range and preserves the original argument-admission order. The windowed route narrows the admitted index interval before scanning.

  1. Validate the output pointer, nonzero count, power-of-two alignment and initialized accounting.
  2. Check bound ordering, page alignment and containment before subtracting addresses.
  3. Scan only the selected frame interval. Reserved and allocated frames break a candidate run.
  4. After the complete run is found, set its allocation bits, update the count and publish its first address.

There is no partial allocation, fallback outside the window, callback or fallible allocation during publication. On refusal the caller's output remains unchanged. Freeing uses the existing shared operation, including its whole-range ownership checks. The allocator still does not identify individual owners or detect an address freed and reused by another caller.

Lesson 4: qualify the actual C implementation on a host

From a Kernel checkout, configure an independent build directory using the existing host test project. It compiles the production allocator, not a rewritten model. The following example uses an arbitrary project checkout and keeps output separate from source:

cmake -S C:/Projects/umicom-kernel/tests/physical_memory -B C:/Builds/kernel-frames -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build C:/Builds/kernel-frames --parallel 2
ctest --test-dir C:/Builds/kernel-frames --output-on-failure

Stop after an error. The project currently registers forty unrestricted-run cases and thirty-six window cases. The host fixtures use numeric addresses and never read or write those physical locations. GCC/Clang warnings are treated as errors.

Inspect cases for a window smaller than the requested run, barriers in the middle, absolute alignment, the highest representable managed range, maximum bitmap capacity and mixed use of both APIs. Refusal checks compare output markers, per-frame states and semantic counters. Structure padding is not used as a substitute for allocator state.

Lesson 5: distinguish host and guest evidence

The diagnostic RISC-V image calls the same allocation service. It borrows and returns a known free four-frame run, allocates a two-frame window with absolute alignment, refuses a conflicting run and an unaligned window, then verifies that ownership returns to the original baseline. It never touches the selected RAM bytes or performs device DMA.

Use the Kernel's configured RISC-V qualification build and its current-image fixture:

cmake --build C:/Builds/kernel-riscv --target umicom-kernel-evidence --parallel 2
ctest --test-dir C:/Builds/kernel-riscv -R "^kernel[.](qualification[.]identity|riscv64[.]physical_memory|riscv64[.]physical_windows)$" --output-on-failure

The expected window markers are physical-window.alignment=pass, physical-window.refusal=pass, physical-window.ownership=pass and UMICOM_KERNEL_PHYSICAL_WINDOWS_READY. The qualification identity must match the current source and ELF. Expected markers are a procedure, not evidence that another machine or source revision has passed.

Lesson 6: understand what a window cannot establish

An address ceiling can express one input to a device allocation policy. It does not prove that a device can access the region. DMA ownership, bus addresses, cache coherence, IOMMU translation, buffer pinning and cancellation require their own implementation and evidence. Do not hand these frame addresses to a device merely because allocation succeeded.

The service does not zero memory, map virtual addresses or protect a stale address from reuse. Reserved boot regions remain mandatory. Calls are serialized by the owner; there is no hidden lock or interrupt policy change.

Exercises and recovery

  1. Initialize thirty-two frames at address 0x1000. Choose a window beginning at 0x5000 and ask for two frames aligned to four frames. Explain why the first eligible address is 0x8000.
  2. Shorten the exclusive end to 0x8000. Expect out-of-memory, even though lower RAM remains free.
  3. Reserve a frame in the middle. Prove that the returned run is wholly after the barrier or that the request fails without changing any bits.
  4. Free a window allocation and request an unrestricted frame. Explain how both operations see the same state.

If a bound is rejected, inspect its units and exclusive-end convention. If allocation reports out-of-memory, inspect fragmentation and alignment before enlarging global RAM. If a host test passes but a guest test fails, retain the first failed operation, source identity and complete guest transcript. Do not treat host success as architecture qualification.

Inspect capacity before choosing a run

A free-frame total does not say whether a contiguous aligned allocation can succeed. Reservations and existing allocations split free space. The read-only window report describes those gaps without taking ownership.

#include "umicom/kernel/physical_window_report.h"
UmicomKernelPhysicalWindowReport report = {0};
UmicomKernelMemoryStatus status = UmicomKernelPhysicalWindowInspect(
    minimum_address, exclusive_end, alignment_frames, &report);
if (status == UMICOM_KERNEL_MEMORY_OK) {
    /* Use largestRunFrames, freeFrames and freeRuns for diagnostics. */
}

The surrounding Kernel code supplies an initialized allocator, a page-aligned nonempty window wholly inside managed RAM, and a nonzero power-of-two alignment measured in frames. The report copies geometry, free/reserved/allocated counts, the count of raw free regions and the longest run that begins at an absolutely aligned frame. Equal longest lengths choose the lowest starting address. A zero run length means none is available; address zero can still be valid when the length is nonzero.

For example, eight free pages separated by eight reserved pages provide eight one-page runs. A request for two consecutive pages fails despite the free total. Alignment may shorten a free region further: a region beginning at physical frame one with four-frame alignment cannot begin an aligned allocation until frame four.

  1. Configure and build the hosted physical-memory project using the earlier commands.
  2. Run ctest --test-dir build/physical-memory --output-on-failure -R "kernel[.]physical_memory[.]report", substituting your chosen build directory.
  3. Review the fragmented, alignment-prefix, aligned-tie and no-reservation cases. Each checks every managed frame before and after inspection.
  4. Build the diagnostic Kernel image and run its existing physical-memory guest checks. Expect physical-window.report=pass before the final window-ready marker.
  5. After a successful report, perform allocation through the ordinary allocator API. Never treat the reported address as already owned.

The complete call must be serialized with allocator changes. A report is neither a lock nor a promise that a later allocation will succeed. The implementation reuses public ownership queries and invariant validation, takes constant stack space, and scans bounded metadata without reading the described RAM. It does not replace boot reservations or establish DMA accessibility. Host tests and synthetic guest execution remain separate from real hardware qualification.

Why a hosted build can pass while the Kernel link fails

C aggregate initialization and assignment can become calls to memset and memcpy. A desktop test executable links a C runtime, so these calls can succeed there. A freestanding Kernel image may have no runtime library and will report undefined symbols at link time.

For mutable boot records, this implementation uses the existing UmicomBootMemoryClear and UmicomBootMemoryCopy helpers. Their reviewed volatile byte accesses prevent substitution with hosted calls. Copying requires valid, nonoverlapping ranges; these helpers are not general MMIO routines. The old aggregate operations remain disabled for engineering review.

cmake --build build/kernel --target umicom-boot-memory-contracts

Use your configured Kernel build directory. This target links the actual report implementation at both Debug and optimized settings without libc and without discarding unused sections. Both links must succeed. Then execute the hosted report suite and the diagnostic guest separately: a link check does not prove the reported counts, and a hosted test does not prove freestanding compatibility.

Keep a run within one physical boundary

An address window and an alignment answer different questions. The window restricts where all frames may lie. Alignment restricts the first address. A boundary restricts whether a run may cross a fixed division in physical address space. For example, a buffer beginning at frame three and containing two frames crosses the boundary between frames three and four, even when one-frame alignment is valid.

UmicomKernelPhysicalMemoryAllocateFramesInWindowWithBoundary combines all three rules using the same allocator. Its third argument, boundaryFrames, is zero to disable the extra rule or a nonzero power of two. The boundaries start at physical address zero, not at the RAM base or the window. All size and alignment arguments are in frames.

UmicomAddress first = 0;
UmicomKernelMemoryStatus status =
    UmicomKernelPhysicalMemoryAllocateFramesInWindowWithBoundary(
        3, 1, 4, 3 * UMICOM_KERNEL_PAGE_SIZE,
        8 * UMICOM_KERNEL_PAGE_SIZE, &first);
if (status == UMICOM_KERNEL_MEMORY_OK) {
    /* With these pages free and managed, first is physical frame four. */
    status = UmicomKernelPhysicalMemoryFreeFrames(first, 3);
}

This fragment requires an initialized allocator that manages the complete requested window. The caller must install boot reservations, serialize access and check both allocation and release. It uses numeric addresses only; successful allocation does not make those addresses safe to dereference.

Request with four-frame boundariesResult when the window is free
Three frames starting at frame oneMay end at frame four exclusively; no crossing occurs.
Three frames, window [3, 8)Skip frame three and begin at frame four.
Three frames, window [3, 6)Out of memory: no complete eligible run lies inside the window.
Five framesOut of memory: no four-frame bucket can contain them.
Boundary threeInvalid alignment: nonzero boundaries must be powers of two.

The implementation calculates the candidate's offset within a boundary and subtracts it from the boundary width. It compares the run count with that remaining space. This avoids multiplying a large boundary by page size or constructing a next-boundary address that could overflow. An exact fit is accepted. Reservations and allocations still break candidate runs, and all ownership changes occur only after a complete eligible run is found.

Verify boundary rules with an independent model

  1. Reconfigure and build the hosted physical-memory project using the earlier commands. All unrestricted, window and report tests remain included.
  2. Run ctest --test-dir C:/Builds/kernel-frames --output-on-failure. The boundary group adds 36 cases. Four exhaustive cases compare 46,080 small requests with an independent candidate model over six frames, all ownership masks and several absolute bases.
  3. The model checks candidate first and last frame numbers using division. Tests compare every frame and all relevant counters, including on refusal. Agreement between two models is useful evidence but does not replace review of shared assumptions.
  4. Build the configured RISC-V evidence image and the umicom-boot-memory-contracts target. Run the existing physical-memory and physical-window guest checks.
  5. Expect physical-window.boundary=pass before the final window-ready marker. Verify the source/ELF identity and retain actual results rather than treating this expected marker as a recorded pass.

If a request fails, first check units and the power-of-two rules, then compare the count with the boundary width and inspect the complete window. A free-run report does not apply this additional boundary constraint: its largest run can still cross a boundary. Do not treat its address as an already allocated buffer or proof that a constrained request will succeed.

These rules do not establish device DMA accessibility, bus-address translation, IOMMU configuration, cache coherence, pinning or hardware ownership. The Kernel still relies on caller serialization and exclusive ownership; it does not identify stale addresses or individual allocation groups.

Observe boundary-constrained capacity

A window can contain three consecutive free frames while only two fit inside the permitted physical boundary. Use UmicomKernelPhysicalBoundaryInspect when planning an allocation with the same window, alignment and boundary parameters. The original UmicomKernelPhysicalWindowInspect retains its boundary-free behavior and report layout.

#include "umicom/kernel/physical_boundary_report.h"
UmicomKernelPhysicalBoundaryReport report;
UmicomKernelMemoryStatus status = UmicomKernelPhysicalBoundaryInspect(
    minimum_address, maximum_end, alignment_frames, boundary_frames, &report);
if (status == UMICOM_KERNEL_MEMORY_OK && report.window.largestRunFrames != 0) {
    /* Inspect report.window.largestFirstFrame; no ownership was acquired. */
}

The fragment assumes admitted page-aligned window bounds and caller serialization with allocator mutation. Zero boundary disables the additional constraint; other values must be powers of two measured in frames. The function uses one shared ownership scan and existing freestanding clear/copy helpers.

For absolute frame numbers 1, 2 and 3, boundary size two divides the window into the buckets [0,2) and [2,4). With alignment one, the longest eligible run starts at frame 2 and has length two. The raw free-region count remains one and the free-frame count remains three. For a window containing only frames 1 and 2, the longest eligible run has length one; the lower starting address wins the tie.

Raw totals, reservations, allocations and free regions describe ownership. Only the largest-run fields apply both alignment and boundary constraints. A nonzero run length makes address zero valid; zero length means no eligible start. The report is not a transferable allocation handle or a promise that memory will still be free later.

Qualify the observation separately

  1. Run the hosted physical-memory suite. The boundary-report cases compare every candidate start with a separate division-based oracle across 80,640 small-state combinations, including all six-frame ownership masks, four RAM origins, three alignments, five boundaries and every nonempty window.
  2. Retain all earlier allocation and report regressions. Passing a new constrained report must not change the original boundary-free API.
  3. Build the RISC-V diagnostic image and both Debug and optimized no-libc memory contracts. This catches hosted memory functions introduced by compiler lowering.
  4. Run the focused physical-window guest check and inspect physical-window.boundary-report=pass together with the current-image identity and process exit.
  5. Keep device DMA, physical hardware, page mapping and cache-coherence claims separate. These fixtures inspect metadata without dereferencing described RAM.

On invalid geometry or an unavailable allocator, the complete previous output remains unchanged. If a later allocation fails, re-inspect under the caller's synchronization; do not treat an older report as ownership. If raw free totals look sufficient but the eligible run is shorter, examine absolute alignment, bucket boundaries and fragmentation before changing the allocation request.

Use an address window for Sv39 page tables

The virtual-memory mapper is a concrete consumer of the physical allocator's window API. A C address type can hold more bits than a hardware page-table field. In the RISC-V supervisor specification, Sv39 combines a 44-bit physical page number with a 12-bit offset. This gives an encoding limit of 256 bytes, exclusive. It does not mean that a machine actually implements or owns that amount of RAM.

The mapper now checks physical-address width before constructing a leaf or allocating intermediate tables. An address of 0x0100000000000000 is page aligned but cannot be represented in the supported PPN field. Shifting it into a PTE would set a reserved bit. Silently masking that bit would be worse: it would map a different physical address.

#include "umicom/kernel/virtual_memory.h"
UmicomAddress physical = (UmicomAddress)0x0100000000000000ULL;
if (UmicomKernelVirtualMemoryIsPhysicalAddressRepresentable(physical) == UMICOM_FALSE) {
    /* Reject or choose a different owned backing frame before mapping. */
}

The query accepts byte addresses and checks only width. Page alignment, virtual-address canonical form and permissions have separate checks. MapPage reports UMICOM_KERNEL_VIRTUAL_MEMORY_INVALID_PHYSICAL_ADDRESS for an otherwise admitted unencodable physical address. It preserves existing mappings and allocation accounting on this refusal. It still does not acquire ownership of a leaf frame or establish that the mapped bytes are accessible.

Page-table backing has a stricter operational need because the Kernel clears those pages. The table allocator intersects managed RAM with the encodable address range and asks the existing window allocator for the lowest eligible frame. It never clears an unencodable frame. If all managed RAM is above the limit, it reports an invalid physical address. If the encodable portion exists but contains no free frame, it reports out of memory, even when frames above the limit remain free.

Validate stored entries before following them

Checking an address before creating a mapping does not validate a page table that has already been stored in memory. A mistaken write can change its address bits or permissions later. The software mapper now checks the supported entry encoding before decoding an intermediate pointer, translating a leaf, accepting a duplicate mapping or unmapping it. Destruction validates the complete hierarchy before releasing its frames.

Bits 54 through 63 must be zero for this mapper's supported Sv39 subset. A writable entry without read permission is also rejected. Intermediate pointers reject the reserved user, accessed and dirty bits. This mapper additionally refuses global intermediate pointers because inherited global permissions are not implemented in its reports. Global leaf mappings remain supported. The two software-use bits, 8 and 9, remain usable. An invalid entry's remaining payload is ignored.

These rules follow the RISC-V supervisor specification within the mapper's documented subset. Svnapot, Svpbmt, large pages and inherited global mappings require separate implementations; recognizing their bit positions does not implement them.

  3. Restore the original entry and verify normal unmapping and destruction. This recovery belongs to the test fixture, which knows the original value; production callers must not guess a replacement for a corrupt entry.
  4. Run the hosted project using the preceding configure and build commands, then select the new cases:
ctest --test-dir C:/Builds/kernel-virtual-memory -R "^kernel[.]virtual_memory[.]entry[.]" --output-on-failure --no-tests=error

Assessment and limits

Explain why a reserved address bit must be rejected before shifting a PPN into a pointer. Then explain why a well-formed pointer can still be unsafe. The address-space root and every referenced table must still be live, trusted Kernel-owned storage. Encoding validation does not establish ownership, detect aliases or cycles, synchronize concurrent changes, validate arbitrary physical pointers, or authorize an actual memory access. The hosted fixture never dereferences the leaf physical address. Retain the existing user-memory and RISC-V hardware-translation regressions when changing this boundary.
