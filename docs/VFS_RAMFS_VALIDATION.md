# Umicom Kernel — VFS and RAMFS validation evidence

The baseline is the committed native Kernel:

```text

```

The source directories used for qualification were reconciled against their
committed Git tree identities: arch, cmake, include, kernel, platform, programs

## Compile and package checks

Both complete Debug and Release cross-builds passed, including the normal Kernel,
the existing separate native programs and the independently linked nested-fault
test image. ELF inspection retains a 64-bit little-endian RISC-V executable with
Kernel entry at `0x80200000`.

A repeated build in each configuration reported `ninja: no work to do`.
The finished source ZIP was applied to a separate copy of the baseline and
cross-built from paths containing spaces. Its native suite was also rebuilt
from those extracted files rather than a different working directory's source.
No stale object file or missing local-only header was used to complete the
package reconstruction.

Production code uses explicit freestanding clearing/copying loops. Successful
linking does not rely on a hosted libc `memset`, `memcpy` or allocator. No source
file is generated by Python or a shell as part of the delivered build.

## New native tests

The standalone `tests/ramfs` project registers 65 cases. Supplying a real,
separately cross-built diagnostic ELF adds the sixty-sixth byte-source/loader
integration case. All 66 passed in these configurations:

| Compiler/configuration | Instrumentation | Result |
|---|---|---:|
| Clang Debug | AddressSanitizer + UndefinedBehaviorSanitizer | 66/66 |
| Clang Release | AddressSanitizer + UndefinedBehaviorSanitizer | 66/66 |
| GCC Debug | AddressSanitizer + UndefinedBehaviorSanitizer | 66/66 |
| Finished ZIP reconstruction, Clang Debug | AddressSanitizer + UndefinedBehaviorSanitizer | 66/66 |

The tests compile the actual VFS, RAMFS, object cache, physical allocator and
checked-address helpers. A test-only wrapper invokes the real allocator except
at the selected allocation/release refusal. The architecture access predicate is
modelled; no host test executes a RISC-V CSR or enters supervisor/user mode.

### Covered behaviours

* Lazy initialisation; stable-owner copy/reinitialisation refusal; mount and
  client pins; partial client close; multiple root pins.
* Canonical paths, name/depth bounds, absent/intermediate file nodes, duplicate
  creation, root protection and nonempty/open-directory refusal.
* Client rights, descriptor restrictions, no escalation through duplication,
  independent Open positions, shared duplicate positions and directory cursors.
* Descriptor capacity, stale tokens, generation retirement and client-local
  token domains.
* Binary data including zero bytes, EOF/short EOF, non-contiguous frames,
  cross-page I/O, sparse gaps, resize growth, cleared shrink/regrowth and append.
* Range/overflow refusal, zero-byte I/O, no-memory prefixes, per-file limits,
  data-page quota and metadata-node quota.
* Name removal while open, same-name replacement, pinned-node retention,
  explicit reap, scrubbing, failed release and retry, closing admission.
* Namespace-epoch invalidation, returned entry copies, counter exhaustion,
  invalid provider operations and unchanged outputs on refusal.
* Deliberately invalid frame state, duplicate backing addresses, incorrect
  parents, cache-guard damage, reference-count corruption and metadata/data alias.

The repeated-lifetime case performs 2,000 create/open/write/unlink/close/reap
cycles without resetting identities or descriptor generations. The mixed-byte
case performs 4,000 deterministic writes/resizes/reads and compares file contents
against a separate byte model. The available-memory sweep uses thirteen budgets.
These are bounded regression checks, not exhaustive fuzzing or a formal proof.

The close-release test injects failure at each release position in a representative
file-plus-cache teardown. After a refusal, already-released pages remain absent,
remaining pages stay owned, and another Close can finish. A separate case checks
failure when the object cache itself is returning its empty backing frame.

### The actual ELF bridge

The optional integration case uses the real RISC-V `umicom-diagnostic.elf`, not a
synthetic header labelled as an executable. Debug and GCC tests used the Debug
ELF; the Clang Release tests used the Release ELF.

It stores the file through the VFS, changes its magic byte, reads it back and
asks the actual executable loader to reject it. It checks that this refusal
allocates no process image. After repairing the file, it reads the bytes again
and uses the existing ProcessCreate implementation to load them.

The entire filesystem is then destroyed and the staging bytes overwritten.
The test checks the private process image against every segment's file bytes
and zero-initialised memory through the existing checked user-memory reader.
Reads respect that service's existing bounded copy limit. Finally it destroys
the image and verifies that the physical allocation count returns to zero.

**No RISC-V instruction is executed in this native bridge.** It proves stored
bytes, parser refusal, copying, zero fill, independence and cleanup. The guest
case separately requires actual execution and system-call return.

## Current-image fixture experiment

An isolated copy was configured with an unusable stand-in emulator path solely
to inspect CTest registration. No emulator result was inferred from that path.
A complete successful build seeded an ELF, whose SHA-256 was saved. A deliberate
`#error` was then inserted into the isolated validation source, and CTest was
asked for only `kernel.riscv64.vfs_ramfs`.

CTest included `kernel.build.current`, the rebuild failed and the dependent VFS
test was **Not Run**. The seeded ELF hash remained unchanged. The stand-in
emulator command was not invoked. None of these destructive test changes is
included in the delivery.

Registration contains 22 tests, including the original separate nested-fault
image and the new VFS test. The latter requires `kernel_current_image`. Its
success expression is `UMICOM_KERNEL_VFS_RAMFS_READY`; explicit Kernel failure
markers remain failures.

## Guest acceptance still required

**RISC-V QEMU is not installed in the local validation environment.** No normal
boot, privilege transition, fault test or new VFS guest pass is claimed here.
The normal Windows build and QEMU CTests remain required before committing.

The new guest sequence contains six cases:

```text
lazy-mount-and-bounded-namespace
cross-page-data-holes-and-resize
descriptor-rights-and-shared-position
directory-iteration-and-change-detection
unlink-keeps-open-image-and-stale-tokens-fail
ram-file-bytes-to-existing-executable-loader
```

The last case loads the file-read diagnostic with identity 701 and argument 7,
destroys its source filesystem, then runs the existing user execution path. It
requires the real EXIT result 741, user-origin ECALL cause 8 and previous
privilege zero. The private process is destroyed afterwards.

Successful output ends with:

```text
vfs.file-sourced-executable=pass
vfs.machine-state=restored
vfs.frame-accounting=restored
vfs.completed-cases=6
vfs.completed-checks=<count>
vfs-ramfs-test=pass
UMICOM_KERNEL_VFS_RAMFS_READY
UMICOM_KERNEL_END
```

The test compares final allocated/free/reserved frame counts with its entry
baseline and compares the saved machine-control fields. Static metadata and
staging buffers increase the protected Kernel image size; its end address and
absolute reserved-frame count are therefore not fixed expected values.

## Not claimed

This batch is not disk persistence, a user filesystem syscall ABI, a shell,
credential-based file permissions, arbitrary mount routing, interrupt-safe or
SMP-safe I/O, a complete POSIX filesystem or a normal interactive boot. Its data
is volatile and its limits are deliberately small. It is the typed Kernel-side
storage and descriptor foundation that those later services can build upon.
