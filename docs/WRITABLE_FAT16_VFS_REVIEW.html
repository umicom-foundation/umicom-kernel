Writable FAT16 through native file services

The persistent filesystem now connects to the native VFS and process file-service ABI. Programs can write, append, resize and manage a bounded FAT16 namespace through granted file rights, and the normal Kernel console can exercise the same owned writable mount.

What this delivery changes

This batch was developed against remote main at 063a758095b48bb818d41aaa23191f3b055c44a3, rechecked before packaging. That revision already includes the persistent file and directory lifecycle, bounded parent growth and moves. The earlier 3daedc9 handoff is historical; directory creation is already in the current repository.

The new work supplies the next connection: a mutable provider and owned mount exposing disk operations through the existing VFS. It adds positional WRITE to the lifecycle API, all mutable provider callbacks, console commands, native model tests and actual U-mode process tests. The delivery contains 524 files: all 501 baseline tracked files plus 23 new files, with 13 existing files updated. Source, synthetic fixtures, build definitions, documentation and this review are included. Git metadata, generated executables and local build directories are excluded.

The implementation follows the repository's C23, canonical naming, source-preservation and native architecture rules. Earlier operation values are retained and superseded predicates are preserved in disabled explanatory blocks. The native user request/result wire layout and service number are unchanged. The internal C lifecycle request gains a trailing offset, so consumers compile against the updated header. [source]

Qualification boundary. This is a bounded persistent Kernel service on the declared QEMU machine. It does not complete the persistent-system alpha, installable OS, recovery or physical-hardware gates.

UmicomKernelDiskWritableMountOpen takes an explicitly selected block domain, device slot, partition, finite timeout and calendar. It owns the lifecycle session, provider and VFS as one stable object. No host path or disk is selected automatically. Admission requires a writable backend with FLUSH support. Read and enumeration use the committed query path through that same exclusive lease. [source]

The provider exclusively borrows the lifecycle owner. It checks that the owner, updater and device remain usable, including admission, handle, claim, DMA ownership, writable state, inner busy states and accepted-operation count. An unexpected direct lifecycle mutation or transport failure blocks further media access. This enforces the single-owner contract; it does not implement external-media change detection or hot swapping. [source]

The process owner attaches mount.vfs through UmicomKernelUserFilesAttach, then grants each fresh task a chosen rights ceiling. File-service requests still copy and validate user memory before invoking the VFS. Disk work happens in the restored Kernel dispatcher state after the trap. The qualification uses real U-mode ECALLs and does not introduce blocking I/O inside a live user address space or interrupt handler. [source]

These native APIs remain independent of Umicom Framework, GUI services, a Data Server and portable userspace service adaptation. A distribution can later choose how applications receive persistent domains. Ordinary console run and runrw retain their existing RAMFS binding; persistent program routing remains explicit future work.

API and operating contracts

Positional writes and size changes

UMICOM_FAT16_LIFECYCLE_WRITE is appended after MOVE, with numeric value 8. A request requires non-null data, 1–4096 bytes, a valid explicit calendar, size == 0 and an offset no later than EOF. Its resulting length is the larger of the old length and checked end position. Existing operations ignore offset. WRITE supports fragmented chains, sector crossings, in-place replacement, empty-file allocation and extension at EOF. [source]

Only the supplied range changes in existing data sectors; other bytes and pre-existing slack outside that range remain intact. New clusters are completely initialised, including sectors beyond the payload. WRITE sets ARCHIVE and the supplied write time, preserving creation and access fields. Shrink uses lifecycle truncation. Growth uses a zero-filled WRITE at the previous EOF, so newly visible bytes are zero even inside old cluster slack.

Append observes the latest accepted size on each serial write. Independent descriptions can alternate append calls without using an obsolete EOF. Zero-byte write and equal-size resize perform no WRITE, FLUSH, timestamp change or commit-count increment, but require WRITE authority, a file without the FAT READ_ONLY attribute and a usable media owner.

Identity, ownership and namespace changes

The 64-record cache uses monotonic node identities rather than recycled slot numbers. Root and independent descriptions pin nodes. Duplicate descriptors share position, append and iteration state; separate opens have separate positions. Accepted write/resize replaces the cached metadata snapshot while preserving identity and pins. The result must match the original entry, name and kind before publication.

Create durably publishes a name without returning a node, so it does not reserve a cache identity. A later lookup/Open can independently return CAPACITY when all records are pinned or EXHAUSTED when identities cannot advance. A successful namespace operation therefore does not guarantee later descriptor admission.

Removal refuses a pinned target before mutation. Re-creating the spelling gets a new identity. Accepted create/removal advances a mount-wide epoch; stale enumeration reports CHANGED without changing cursor or output. File writes and size changes leave the epoch intact, and refused mutations do not invalidate streams. Epoch and accepted-count exhaustion are checked before disk writes. [source]

A direct lifecycle CREATE with 4096 initial bytes and parent growth can exceed the shared eight-cluster allocation budget. VFS Create publishes an empty file and writes separately. Complete-sector staging and whole-volume proof bounds can refuse other operations earlier; the reported size ceiling is not a promise that every otherwise-valid request is admissible.

Acceptance, uncertainty and cleanup

A successful non-empty VFS write means the dirty guards, ordered data/FAT/directory publication, FLUSH barriers, sector readback and clean Finish were accepted. Caller data is snapshotted before transport callbacks. Metadata and the complete requested byte count are published only after acceptance. Namespace and resize changes use the same explicit Stage/Finish machinery. [source]

Failure reports zero accepted VFS bytes. That does not prove the disk stayed unchanged: submitted bytes may already be visible or durable. The retained result distinguishes phase, submitted/completed sectors, verification, flush evidence and final-acknowledgement uncertainty. A late failure can leave clean-looking bytes without accepted completion. Blind retry would discard this distinction.

The exact result remains in mount.lifecycle.lastResult, with detail in mount.lifecycle.commit.updater.lastDiskStatus, lastBlockStatus and lastCleanupStatus. VFS status is a coarser classification; trusted diagnostics can inspect the lifecycle evidence.

After media failure, data access and mutations are retired for that lifetime, including no-op mutations. Cached stat returns the last accepted snapshot, not a fresh inspection of failed-write bytes. Local validation, unpin and close continue to work. Close releases clients/process attachments, VFS root, provider and lifecycle in reverse order. Outstanding clients prevent unmount even without descriptors. Reset or frame-release failure retains CLOSING ownership for retry. Close never performs an implicit Finish. [source]

Persistence has explicit limits. There is no journal, rollback, automatic repair, multi-operation transaction, power-loss atomicity or sector-atomicity claim. Bounded interruption detection and retained results describe what is known after failure.

Review findings resolved

Review corrected unlink requests to keep unused DELETE/REMOVE_DIRECTORY calendars zero. It strengthened readiness and media retirement after lifecycle BAD_STATE/RELEASE_FAILED, so cached lookup or no-op operations cannot bypass a failed updater or device. Regressions exercise updater CLOSING, device FAULTED and actual transport timeout while retaining local release paths. Accepted write/resize metadata also has explicit original-entry and name/kind consistency checks.

The real guest exposed two integration requirements. Its long sequence exceeded the inherited 32-call process budget, so it was divided into three process lifetimes within that limit. Its dedicated boot now establishes normal boot's parked-timer contract before scheduling. The production budget and acceptance gates were preserved. Console review checked all 13 parser entries, argument counts, help, binary escaping, output after successful close and retained cleanup.

Real native processes and fresh-boot readback

The writer image runs three U-mode lifetimes: data writer, namespace/allocation-reuse continuation and reduced-rights reader. They use the copied file ABI and scheduler ownership, each within the unchanged call limit. Twelve accepted mutations leave /WORK/LOG.BIN at 900 bytes. [source]

Further assertions reject an invalid user buffer before mutation, check duplicate rights and shared offsets, require directory CHANGED after namespace mutation, and refuse WRITE/CREATE/writable Open under reduced task rights. A process exits with an open descriptor so terminal cleanup must close it before reap. An attachment with no tasks still blocks premature unmount. Frame accounting and machine state must be restored before readiness is accepted.

The independent oracle was specified before the writer ran. Its expected bytes come from literal fixture layout and operation effects, without using production plans/results as the expectation. A separate immutable VFS boot reopens the file and compares all 8,388,608 bytes, including FAT mirrors, reclaimed clusters, directory records, slack and unrelated bytes. Host CTest also hashes each role, refuses the checked source as the writable destination and cleans up the disposable copy. [source]

In the fixture, WORK uses cluster 5. LOG grows through 8, 10 and 11; truncation frees 11. TEMP and SUB each reuse/release 11. The final free cluster retains SUB's canonical dot records, and its deleted directory slot remains as predicted. A file-content read alone would miss incorrect FAT mirrors, unrelated-sector damage or incorrect allocation reuse.

Extract, build, test and run

Extract the source ZIP directly over the committed checkout. Repository files are at the archive root, without an extra enclosing directory.

1. Extract

Expand-Archive -LiteralPath "$env:USERPROFILE\Downloads\Umicom_Kernel_Writable_FAT16_VFS.zip" `
    -DestinationPath "C:\umicom\umicom-kernel" -Force
Set-Location "C:\umicom\umicom-kernel"

2. Configure, build and run the complete preset

cmake --preset riscv64-clang-debug
cmake --build --preset riscv64-clang-debug --parallel 2
ctest --preset riscv64-clang-debug --output-on-failure --no-tests=error

Commit after configuration, build and tests succeed. The preset registers the new writable group when QEMU is found.

3. Commit and push

git add -A
git commit -m "feat(kernel): add writable FAT16 VFS and native process file access"
git push

4. Prepare one disposable test disk

This copy step resets the test disk to the synthetic original. Run it once for a new test; keep the same copy across reboot.

New-Item -ItemType Directory -Force `
    -Path ".\build\riscv64-clang-debug\fixtures" | Out-Null
Copy-Item -LiteralPath ".\tests\fat16_file_commit\fixture.raw" `
    -Destination ".\build\riscv64-clang-debug\fixtures\umicom-writable-vfs-test.raw" -Force

5. Boot the normal Kernel with that disk

& "C:\msys64\ucrt64\bin\qemu-system-riscv64.exe" `
    -machine "virt,aclint=off" `
    -bios ".\build\riscv64-clang-debug\bin\umicom-system.elf" `
    -display none `
    -monitor none `
    -chardev "stdio,id=console,signal=off" `
    -serial "chardev:console" `
    -m 128M `
    -smp 1 `
    -no-reboot `
    -global virtio-mmio.force-legacy=false `
    -drive "file=.\build\riscv64-clang-debug\fixtures\umicom-writable-vfs-test.raw,if=none,format=raw,id=umicomdisk,readonly=off,cache=writeback,rerror=report,werror=report" `
    -device "virtio-blk-device,drive=umicomdisk,write-cache=on,logical_block_size=512,physical_block_size=512,num-queues=1"

6. Create and read a persistent file

Use the slot printed by disks; the qualified single-disk command reported slot 7. The leap-day calendar is deterministic sample data.

disks
mountdiskrw 7 0 2044-02-29T23:58:56
diskmkdir /WORK
diskcreate /WORK/NOTE.TXT
diskwrite /WORK/NOTE.TXT 0 "hello"
diskappend /WORK/NOTE.TXT " world"
diskrwcat /WORK/NOTE.TXT
diskrwls /WORK
diskrwinfo
unmountdiskrw
poweroff

Expect hello world, an 11-byte NOTE.TXT and four accepted mutations. Each command completes acceptance; no extra fatfscommit is needed for this interface.

7. Prove persistence after reboot

Run the same QEMU boot command again, without repeating Copy-Item, then enter:

disks
mountdiskrw 7 0 2044-02-29T23:58:56
diskrwcat /WORK/NOTE.TXT
diskrwls /WORK
unmountdiskrw
poweroff

Expect hello world again. In a fresh boot, diskresize /WORK/NOTE.TXT 16 exposes five zero bytes, displayed as \x00. diskdelete removes closed files; diskrmdir removes empty directories.

Next substantial checkpoint

A useful next integration is bounded executable/configuration loading from an explicitly selected persistent mount, with normal process ownership and granted rights, followed by fresh-boot qualification. That would let the ordinary interactive process route consume disk-backed programs. It needs its own admission, executable validation, lifetime and failure tests.

The persistent-system alpha gate stays open. Move/rename exists in the separate lifecycle API; the VFS wire contract has no rename operation. Persistent orphan files, long filenames, sparse files, mount crossing, asynchronous I/O, safe installation, authenticated accounts, networking, persistent boot policy and recovery/update rollback remain independent work.
