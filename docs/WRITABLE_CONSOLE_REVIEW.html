Command failures now explain the recovery step

The earlier mountdiskrw 7 @ 2044-02-29T23:58:56 attempt failed before mount admission. Partition selection requires a decimal primary-partition index from 0 to 3, and the synthetic fixture uses 0. The old dispatcher returned its invalid-argument status without visible command-specific guidance, leaving the later bad-state messages difficult to interpret.

The exact malformed partition command now prints:

mountdiskrw=invalid-argument field=partition
PARTITION must be decimal 0..3; use 0 for the first partition.
usage: mountdiskrw SLOT PARTITION YYYY-MM-DDTHH:MM:SS

A corrected mount with 0 is still permitted in the same boot because invalid arguments never consume the mount owner. A following mutation without any admitted mount explains what is missing:

No writable disk is mounted. Run disks, then mountdiskrw SLOT PARTITION YYYY-MM-DDTHH:MM:SS.
PARTITION is decimal 0..3; use 0 for the first partition.
diskmkdir=bad-state committed-operations=0

All 13 writable-console commands now have usage text for malformed argument counts that reach their dispatcher. Numeric slot, partition, offset and size parsing identifies the offending field. Calendar validation identifies invalid syntax or an invalid FAT calendar value. The shared parser still enforces its existing maximum of four tokens; input beyond that limit follows its existing syntax-error path.

The output distinguishes an unused owner from an active mount, retained cleanup, a closed single-use lifetime, and an admitted operation that encountered an actual media or transport failure. An unused structure no longer prints zero-initialised diskrw.media=ok as though a device had been examined. Once admission occurs, the media, block and cleanup evidence remains available.

Diagnostic callbacks also receive the existing reentry protection before a mount owner exists. This closes a feedback-path gap without allowing a callback to recursively admit, mutate or close the owner. The original shell ownership and single-use mount lifetime remain part of the contract; failed admitted operations still follow their existing cleanup rules.

The disks footer now explains that its raw-read commands use a separate owner. It no longer leaves the impression that the Kernel as a whole cannot mount or write a filesystem. Superseded source fragments remain in explanatory disabled blocks, following the repository's source-preservation policy.

One PowerShell command exercises two real boots

& ".\scripts\Test-UmicomKernelWritableConsole.ps1" -CheckSyntaxDiagnostics

scripts/Test-UmicomKernelWritableConsole.ps1 launches the normal bin/umicom-system.elf and interacts through its real serial console. It does not require clipboard support or Python. QEMU executable discovery includes the usual MSYS2 UCRT64 location, with an explicit -QemuPath override available.

  1. Verify the known immutable FAT16 fixture, create a new unique run directory, and copy that fixture to a disposable writable image.
  2. Reserve a loopback TCP listener before starting QEMU. QEMU connects its serial backend to that listener.
  3. Run disks, discover the single successfully probed block slot, and mount primary partition 0 with the explicit test calendar.
  4. Create /WORK/NOTE.TXT, write and append its contents, and verify every status, accepted-operation count, file content and byte count.
  5. Unmount, power off, confirm the shutdown marker and wait for QEMU to exit successfully.
  6. Start a fresh QEMU process against the same disposable image, read the file again, verify its size, and shut down cleanly.
  7. Check that the source fixture is unchanged and that the complete image is identical before and after the second boot's readback.

Input is paced by the guest: the script waits for each character's echo before sending the next character, and for the next prompt before issuing another command. Each command has a finite deadline; waiting for individual characters does not extend that deadline. This avoids both manual typing and a burst of pasted input into the guest UART.

The optional -CheckSyntaxDiagnostics switch adds the exact @ failure, checks that the mount is still unused, then proves that the corrected mount works. Build this update before using that switch. Default execution also works with the preceding writable-VFS firmware.

The script accepts -BuildDirectory and -TimeoutSeconds (5–300 seconds, default 60). Relative build paths resolve from the repository containing the script. Executable and build paths with spaces were exercised. Build paths containing commas are refused because the drive specification uses QEMU's comma-separated option syntax.

Every invocation gets its own test disk. The runner has no arbitrary existing-disk parameter and never overwrites an earlier run. It retains the disposable image, serial/stdout/stderr logs and result.json under the build directory and prints their location.

Each output stream is capped at one MiB. A failed runtime check preserves evidence, closes the listener and stops only the QEMU process owned by that invocation. Preflight failures occur before a writable run is created. The script uses ordinary PowerShell invocation and does not change execution-policy settings.

For occasional interactive use in Windows Terminal, Microsoft documents Ctrl+Shift+V and Shift+Insert among the default Paste bindings. Send one command and wait for the next prompt. In this guest console, Ctrl+C cancels the current input line. The automatic runner removes the need to paste this sequence at all.

Extract, build, test, commit and push

Expand-Archive -LiteralPath "$env:USERPROFILE\Downloads\Umicom_Kernel_Console_Persistence_Fix.zip" `

cmake --preset riscv64-clang-debug

The last command launches the Kernel twice and checks the complete normal-console sequence. It uses a fresh disposable image, so the manual test disk containing your successful result is preserved. After the commands have completed successfully:

git push

Optional interactive boot of your existing manual disk

The manual reboot test is already complete. If you want to inspect its saved file again, the following command uses the existing umicom-writable-vfs-test.raw from that test. Do not replace that disk with a fresh fixture before reading it.

& "C:\msys64\ucrt64\bin\qemu-system-riscv64.exe" `
    -machine "virt,aclint=off" `
    -bios ".\build\riscv64-clang-debug\bin\umicom-system.elf" `
    -display none `
    -monitor none `
    -chardev "stdio,id=console,signal=off" `
    -serial "chardev:console" `
    -m 128M `
    -smp 1 `
    -no-reboot `
    -global virtio-mmio.force-legacy=false `
    -drive "file=.\build\riscv64-clang-debug\fixtures\umicom-writable-vfs-test.raw,if=none,format=raw,id=umicomdisk,readonly=off,cache=writeback,rerror=report,werror=report" `
    -device "virtio-blk-device,drive=umicomdisk,write-cache=on,logical_block_size=512,physical_block_size=512,num-queues=1"
